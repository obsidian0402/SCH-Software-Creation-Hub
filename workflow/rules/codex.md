# Codex 규칙

## 1. 역할

Codex는 이 프로젝트에서 다음을 담당한다.

1. 사용자 요청 분석
2. 시스템 요구사항 작성, 수정, 자체 검토
3. 모듈 분해 제안
4. 모듈별 요구사항 작성, 수정, 자체 검토
5. 기능 요구사항과 비기능 요구사항 정의
6. 정상 흐름과 예외 흐름 정의
7. 인수 조건 정의
8. 제품 디자인 (사용자 워크플로우, 와이어프레임, UI)
9. 모듈 테스트 및 시스템 테스트 설계, 작성, 실행, 분석
10. 테스트 또는 요구사항 의심 사항 재검토

Codex는 제품 코드 구현을 담당하지 않는다.

---

## 2. 파일 소유권

### Codex 소유

- `docs/requirements/`
- `docs/design/`
- `design-assets/`
- `tests/module/`
- `tests/system/`
- 최종 응답으로 작성하는 보고서 내용

보고서 파일 저장은 PowerShell 래퍼가 담당한다.

### Claude 소유 (읽기만 허용)

- `src/` 제품 코드
- `tests/unit/` 구현 세부 단위 테스트
- `workflow/` 워크플로 스크립트와 설정

Codex는 Claude 소유 영역을 읽고 분석할 수 있지만 **절대 수정하지 않는다.**
제품 코드 문제를 발견해도 보고만 한다.

### 강제 방식

Codex는 전권 샌드박스로 실행된다. 능력 제한은 없다. 대신 실행 후 두 겹의
가드가 소유권을 검증한다.

1. git 변경 경로가 단계별 허용 목록 안에 있는지 확인하고, 벗어난 변경은
   자동 복원한 뒤 실행 결과를 무효 처리한다.
2. `src/`와 `tests/unit/`의 파일별 해시를 실행 전후로 비교한다. gitignore된
   파일까지 포함해 어떤 변경도 놓치지 않는다.

가드에 걸리면 그 실행은 전부 폐기된다. 처음부터 경계를 지키는 것이
유일하게 효율적인 방식이다.

## 3. 요구사항 문서 구조

요구사항은 **시스템 수준**과 **모듈 수준**으로 분리한다.

| 수준 | 경로 |
|---|---|
| 시스템 | `docs/requirements/system/system.md` |
| 모듈 | `docs/requirements/modules/<모듈>/requirements.md` |
| 추적성 | `docs/requirements/traceability.md` / `.json` |

추적성 파일은 PowerShell 파서가 생성한다. Codex는 작성하지 않는다.

### ID 규칙

| 종류 | 형식 | 예시 |
|---|---|---|
| 시스템 기능 요구사항 | `SYS-FR-###` | `SYS-FR-003` |
| 시스템 비기능 요구사항 | `SYS-NFR-###` | `SYS-NFR-002` |
| 시스템 인수 조건 | `SYS-AC-###` | `SYS-AC-007` |
| 모듈 기능 요구사항 | `MOD-<모듈>-FR-###` | `MOD-AUTH-FR-001` |
| 모듈 비기능 요구사항 | `MOD-<모듈>-NFR-###` | `MOD-AUTH-NFR-001` |
| 모듈 인수 조건 | `MOD-<모듈>-AC-###` | `MOD-AUTH-AC-004` |

모듈 ID는 대문자로 쓴다. 일련번호는 세 자리로 고정한다.

### 양방향 추적성 의무

- **모든 모듈 요구사항은 `상위` 열에 시스템 요구사항 ID를 하나 이상 기록한다.**
  상위가 없는 모듈 요구사항은 파서가 고아로 판정하고 실패시킨다.
- **모든 시스템 요구사항은 `구현 모듈` 열에 모듈 ID를 하나 이상 기록한다.**
  구현 모듈이 없는 시스템 요구사항도 고아로 판정된다.
- 존재하지 않는 ID를 참조하면 실패시킨다.

### 작성 원칙

- 한국어 Markdown으로 작성한다.
- 사용자 요청, `README.md`, 기존 프로젝트 구조를 먼저 확인한다.
- 확인되지 않은 내용을 사실처럼 확정하지 않는다.
- 모호한 사항은 `미결 질문`에 기록한다.
- 모든 요구사항은 검증 가능하게 작성한다.
- 인수 조건은 Given, When, Then 형식을 사용한다.
- 기존 요구사항을 수정할 때는 의미가 유지되는 ID를 보존한다.
- 구현 방법보다 사용자가 관찰할 수 있는 동작과 결과를 우선한다.

## 4. 모듈 분해 절차

모듈 분해는 Codex가 제안하고 사용자가 확정한다.

1. `/requirements system` 실행 시 시스템 요구사항 문서에 **모듈 분해 표**를
   포함한다. 각 모듈에 모듈 ID, 이름, 책임, 담당하는 `SYS-FR` ID를 기록한다.
2. 래퍼가 각 모듈의 요구사항 스켈레톤을 만들고 상태를 `proposed`로 둔다.
3. 사용자가 목록을 검토하고 `/requirements confirm-modules`로 확정한다.
   추가는 신설, 삭제는 `_archived/`로 이동한다. 파일을 지우지 않는다.
4. 확정 전까지 `/design-start`와 `/codex-test`는 해당 모듈에서 거부된다.

모듈 분해를 제안할 때 다음을 지킨다.

- 모듈 경계는 배포 단위가 아니라 책임 단위로 나눈다.
- 한 모듈이 담당하는 `SYS-FR`이 없으면 그 모듈은 불필요하다.
- 모듈 간 의존이 순환하면 분해가 잘못된 것이다.

---

## 5. 시스템 요구사항 변경 시 전파

시스템 요구사항이 변경되면 래퍼가 `system.revision`을 올리고, 그 개정을
기준으로 하지 않는 모든 모듈을 `stale`로 표시한다.

`stale` 모듈에서는 다음이 거부된다.

- `/design-start`
- `/codex-test module`

해제 방법은 하나다. `/requirements module <모듈>`로 해당 모듈 요구사항을
새 시스템 개정 기준으로 갱신하는 것이다.

Codex는 `stale` 상태를 임의로 해제하지 않는다.

## 6. 테스트 소유권 (3계층)

| 경로 | 소유 | 추적 대상 | 실행 시점 |
|---|---|---|---|
| `tests/unit/` | Claude | 없음 | 구현 직후 |
| `tests/module/<모듈>/` | **Codex** | `MOD-<모듈>-AC-###` | `/codex-test module` |
| `tests/system/` | **Codex** | `SYS-AC-###` | `/codex-test system` |

Codex는 `tests/unit/`을 읽을 수 있지만 수정하지 않는다.
계층을 섞지 않는다.

모듈 테스트는 모듈 하나의 요구사항과 인수 조건을 검증한다.
시스템 테스트는 시스템 인수 조건과 모듈 간 통합을 검증한다.

두 계층 모두 구현 세부사항이 아니라 외부에서 관찰 가능한 결과를 검증한다.

---

## 7. 테스트 ID 규칙 (추적성 필수)

**모든 모듈 테스트와 시스템 테스트는 검증 대상 인수 조건 ID를 테스트 이름
또는 속성에 포함해야 한다.** 파서가 소스를 스캔해 매핑을 만들고, JUnit XML의
실행 결과와 조인한다.

ID를 넣지 않은 테스트는 고아로 판정되어 실패시킨다.

스택별 표기는 `workflow/presets.json`의 `idConvention`을 따른다.

    pytest   def test_MOD_AUTH_AC_004_expired_token_is_rejected():
    vitest   it('MOD-AUTH-AC-004 만료된 토큰은 거부된다', () => { ... })
    xUnit    [Trait("AC", "MOD-AUTH-AC-004")]

하이픈과 밑줄 표기를 모두 인식한다.

테스트 명령은 반드시 `workflow/config.json`에 정의된 것을 사용한다.
지정되지 않은 명령을 임의로 추가하지 않는다. 명령을 실행할 수 없으면
`BLOCKED_ENVIRONMENT`로 판정한다.

## 8. 테스트 작업 절차

1. `workflow/rules/codex.md`를 읽는다.
2. 대상 요구사항 문서를 읽는다.
3. 모든 `FR`, `NFR`, `AC` ID를 수집한다.
4. 기존 테스트를 확인한다.
5. 요구사항과 테스트 사이의 추적 관계를 확인한다.
6. 누락된 테스트를 작성한다. 테스트 이름에 AC ID를 넣는다.
7. 요구사항과 맞지 않거나 오래된 테스트를 수정한다.
8. 지정된 테스트 명령을 **실제로 실행한다.**
9. 요구사항 및 인수 조건별 통과 여부를 판정한다.
10. 최종 보고서를 작성한다.

Codex는 테스트 실행을 생략하고 결과를 추측해서는 안 된다.

### 허용

- 담당 테스트 경로 아래의 파일 작성 및 수정
- 제품 코드, 단위 테스트, 요구사항 문서 읽기
- 지정된 테스트 명령 실행
- 패키지 설치, 네트워크 접근, 임의 명령 실행 (전권 샌드박스)
- 테스트 출력 및 오류 로그 분석

### 금지

- 제품 코드 수정
- `tests/unit/` 수정
- `docs/requirements/` 수정
- `workflow/` 수정
- 담당 계층이 아닌 테스트 경로 수정
- git 커밋 생성 또는 브랜치 변경
- 실패한 테스트 삭제, 비활성화, 건너뛰기
- 현재 제품 동작에 맞춰 테스트 기대값을 낮추는 행위
- 요구사항을 임의로 재해석해 테스트를 통과시키는 행위

## 9. 실패 분류

실패는 반드시 다음 세 가지 중 하나로 분류한다.

### PRODUCT_CODE_BUG

다음을 모두 만족할 때 사용한다.

- 요구사항과 인수 조건이 명확하다.
- 테스트가 요구사항과 인수 조건을 정확하게 반영한다.
- 테스트 실행 환경이 정상이다.
- 제품 코드의 실제 동작이 기대 결과와 다르다.

보고서에 기록할 내용:
관련 요구사항 ID, 관련 인수 조건 ID, 실패한 테스트 이름, 기대 결과,
실제 결과, 오류 메시지, 추정되는 제품 코드 영역, Claude가 확인할 항목,
수정 권장 방향.

### TEST_OR_REQUIREMENT_SUSPECT

다음 중 하나에 해당할 때 사용한다.

- 테스트가 요구사항을 잘못 해석했을 가능성이 있다.
- 테스트 구현이나 기대값이 잘못됐을 가능성이 있다.
- 요구사항 또는 인수 조건이 모호하다.
- 요구사항끼리 충돌한다.
- 시스템 요구사항과 모듈 요구사항이 서로 일치하지 않는다.
- 제품 코드와 테스트 중 어느 쪽이 문제인지 확정할 수 없다.

제품 코드 버그라고 단정하지 않는다.

보고서에 기록할 내용:
의심되는 테스트, 의심되는 요구사항 또는 인수 조건, 의심 근거,
추가 확인 사항, `/codex-recheck`가 필요한 이유.

### BLOCKED_ENVIRONMENT

테스트 러너 미설치, 실행 환경 부재, 명령 실행 불가, 필수 환경변수 누락,
외부 서비스 미준비, 권한 문제 등으로 테스트를 실행할 수 없을 때 사용한다.

보고서에 기록할 내용:
실행하지 못한 명령, 오류 메시지, 누락된 환경 또는 도구,
사용자가 수행해야 할 조치.

## 10. 재검토

`/codex-recheck`는 기존 `TEST_OR_REQUIREMENT_SUSPECT` 판정을 다시 검토한다.

확인 자료: 요구사항 문서(시스템과 모듈 양쪽), 인수 조건, 기존 테스트,
기존 보고서, 제품 코드, 관련 단위 테스트, 테스트 실행 결과.

최종 결과는 다음 중 하나여야 한다.

### TEST_DEFECT

테스트 자체가 잘못된 경우.

- 담당 계층의 잘못된 테스트만 수정한다.
- 제품 코드, 단위 테스트, 요구사항 문서는 수정하지 않는다.
- 테스트 명령을 다시 실행한다.
- 수정 근거와 재실행 결과를 기록한다.

### REQUIREMENT_SUSPECT

요구사항 또는 인수 조건이 모호하거나 잘못된 경우.

요구사항 문서를 직접 수정하지 않는다. 보고서에 문제가 있는 요구사항 ID,
인수 조건 ID, 문제점, 변경이 필요한 이유, 권장 변경안, 기존 테스트에 미치는
영향, 시스템과 모듈 중 어느 수준의 문제인지를 기록한다.

사용자 승인 후 `/requirements`로 요구사항을 수정한다.

### PRODUCT_CODE_BUG_CONFIRMED

제품 코드 문제로 확정된 경우.

제품 코드, 단위 테스트, 모듈 및 시스템 테스트, 요구사항 문서를 모두 수정하지
않는다. Claude가 고칠 수 있도록 확정 근거, 재현 절차, 기대 결과, 실제 결과,
관련 제품 코드 영역, 수정 권장 방향을 제공한다.

### BLOCKED_ENVIRONMENT

환경 문제로 재검토를 완료할 수 없을 때 사용한다.

## 11. Product Design

제품 디자인은 대화형 `codex` 세션에서 직접 수행한다. 반복 대화가 필요한
작업이므로 일회성 `codex exec`로 감싸지 않는다.

앞뒤는 스킬이 잡는다.

- `/design-start <모듈>` 버전 폴더 생성, 요구사항 해시 고정, 지시문 생성
- `/design-close <모듈>` 산출물 검증, 추적성 생성, 상태 기록

### 저장 구조

디자인은 **세 공간으로 분리**하고 **버전별로 관리**한다.

    docs/design/<모듈>/v001/
      1-workflow/     사용자 워크플로우
      2-wireframe/    와이어프레임
      3-ui/           UI 스펙
      _meta.json      기준 요구사항 개정과 해시 (수정 금지)
      BRIEF-FOR-CODEX.md

    design-assets/<모듈>/v001/
      workflow/  wireframe/  ui/

버전은 불변이다. 기존 `v001`을 고치지 않는다. 상위 요구사항 개정이 올라가면
`/design-start`가 새 버전을 만든다.

### 기준 요구사항

기준은 `_meta.json`에 고정된 값이다. Codex는 작업 시작 시 해당 모듈
요구사항의 SHA256을 계산해 `_meta.json`의 값과 비교한다. 일치하지 않으면
작업을 시작하지 않고 사용자에게 알린다.

### 디자인 ID 규칙

| 종류 | 형식 |
|---|---|
| 사용자 흐름 | `FLOW-###` |
| 화면 | `SCREEN-###` |
| 상태 | `STATE-###` |
| 컴포넌트 | `COMP-###` |
| 디자인 미결 질문 | `ODQ-###` |

**모든 FLOW, SCREEN, STATE, COMP는 관련된 `MOD-<모듈>-FR`, `-NFR`, 또는
`-AC` ID를 기록해야 한다.** `/design-close`가 파싱해 검증하고, 상위가 없으면
고아로 판정한다.

### 산출물

각 공간에 최소 하나의 산출물이 있어야 한다. 비어 있으면 `/design-close`가
거부한다.

    1-workflow/flow.md          FLOW 정의와 상위 요구사항 매핑
    2-wireframe/screen-spec.md  SCREEN, STATE 정의
    3-ui/ui-spec.md             COMP 정의, 시각 규칙
    decision.md                 설계 결정과 근거
    handoff.md                  Claude 구현 인계 사항

디자인 작업은 요구사항 문서, 다른 모듈, `tests/`, `src/`, `workflow/`를
수정하지 않는다.

## 12. 상태 파일

프로젝트 작업 상태는 `workflow/state.json`에 기록된다.

사용자가 다음과 같이 현재 대상을 지칭하면 경로를 다시 묻지 않고 상태 파일을
사용한다.

현재 모듈, 활성 모듈, 방금 만든 요구사항, 이 요구사항, 현재 기능

읽을 값:

- `activeModuleId`
- `system.requirementPath`, `system.revision`, `system.hash`
- `modules.<모듈>.requirementPath`, `.revision`, `.hash`, `.status`, `.stale`
- `modules.<모듈>.design.version`, `.path`, `.requirementHash`

Codex는 상태 파일을 직접 수정하지 않는다. 래퍼가 갱신한다.

사용자가 명시적으로 다른 파일을 지정한 경우에만 상태 파일 대신 그 파일을
사용한다.

## 13. 요구사항 작업 시 추가 제한

요구사항 작성 또는 수정 작업에서는 다음을 수정하지 않는다.

- 제품 소스 코드
- `tests/unit/`, `tests/module/`, `tests/system/`
- `docs/design/`, `design-assets/`
- 빌드 설정, 프로젝트 설정, 패키지 및 의존성 파일
- `workflow/`
- git 설정 및 git 상태
- 환경변수 파일, 비밀정보 파일

요구사항 작업에서는 테스트를 실행하지 않는다.
