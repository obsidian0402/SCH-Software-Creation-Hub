# 수행 작업

1. `workflow/rules/codex.md`를 읽는다.
2. 기존 보고서에서 의심 항목을 추출한다.
3. 요구사항 문서를 읽는다. 시스템과 모듈 양쪽을 확인한다.
4. 해당 인수 조건을 정확히 해석한다.
5. 기존 테스트 구현을 읽는다.
6. 제품 코드와 관련 단위 테스트를 읽는다.
7. 어느 쪽이 잘못됐는지 판정한다.
8. 판정에 따라 아래 처리 절차를 따른다.
9. 재검토 보고서를 작성한다.

# 최종 판정과 처리

## TEST_DEFECT

테스트 자체가 잘못된 경우.

- {{TEST_DIRECTORY}} 아래의 잘못된 테스트만 수정한다.
- 제품 코드, 단위 테스트, 요구사항 문서는 수정하지 않는다.
- 테스트 명령을 **다시 실행한다.**
- 수정 근거와 재실행 결과를 기록한다.

## REQUIREMENT_SUSPECT

요구사항 또는 인수 조건이 모호하거나 잘못된 경우.

- 요구사항 문서를 **직접 수정하지 않는다.**
- 시스템 수준 문제인지 모듈 수준 문제인지 명시한다.
- 권장 변경안과 기존 테스트에 미치는 영향을 기록한다.

## PRODUCT_CODE_BUG_CONFIRMED

제품 코드 문제로 확정된 경우.

- 제품 코드, 단위 테스트, 모듈 및 시스템 테스트, 요구사항 문서를 모두
  수정하지 않는다.
- Claude가 고칠 수 있도록 재현 절차와 근거를 제공한다.

## BLOCKED_ENVIRONMENT

환경 문제로 재검토를 완료할 수 없는 경우.

- 필요한 환경과 사용자 조치를 명확히 기록한다.

# 금지

- 제품 코드 수정
- 단위 테스트 수정
- 요구사항 문서 수정
- `workflow/` 수정
- 담당 계층이 아닌 테스트 경로 수정
- git 커밋 또는 브랜치 변경
- 실패한 테스트 삭제, 비활성화, 건너뛰기
- 판단이 어려울 때 제품 코드 버그로 단정하는 행위
