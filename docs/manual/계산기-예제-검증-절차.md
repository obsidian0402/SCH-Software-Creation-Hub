# 계산기 예제 검증 절차

> 이 문서는 **어떻게 검증하는가**를 다룬다. 워크플로 사용법 자체는
> [`workflow/GUIDE.md`](../../workflow/GUIDE.md)에 있다.

---

## 0. 왜 이 문서가 필요한가

`workflow/GUIDE.md` 11절 "알려진 한계"에 다음과 같이 적혀 있다.

> 구문 검사, JSON 유효성, 프롬프트 자리표시자 대조, 함수 호출 대조는 통과했다.
> 그러나 **실제 Codex 왕복은 아직 한 번도 하지 않았다.**

즉 이 프레임워크는 지금까지 서류상으로만 완성되어 있고, 실제 `codex` CLI와
왕복하며 전체 파이프라인(요구사항 → 모듈 확정 → 모듈 요구사항 → 디자인 →
구현 → 모듈 테스트 → 시스템 테스트 → 추적성 생성)을 끝까지 돌려본 적이
없다. "계산기 만들기"는 이 전체 구간을 가장 적은 비용으로 완주할 수 있는
최소 예제로 선택한 것이다.

**검증 대상은 두 층이다.**

1. **계산기 앱 자체** — 사칙연산이 정확히 동작하는가
2. **워크플로 프레임워크** — 스크립트, 가드, 상태 전이, Codex 응답 파싱이
   문서(`GUIDE.md`, `README.md`, `workflow/rules/*.md`)에 적힌 대로 실제로
   동작하는가

이번 검증의 목적은 (2)다. 계산기 자체의 완성도는 부차적이며, 오히려
**의도적으로 버그를 심어 실패 경로까지 밟아보는 것**이 검증의 핵심이다.

## 2. 사전 점검

### 2.1 현재 저장소 상태 확인

검증을 시작하기 전에 현재 작업 트리를 정리한다. 특히 `git diff`로 Codex의
변경 범위를 눈으로 확인해야 하는 vibe 모드(§4.1)에서는 시작 시점이
지저분하면 이후 비교가 불가능해진다.

```powershell
git status
git diff workflow/scripts/Common.ps1 workflow/scripts/init-workspace.ps1
```

현재 다음이 미커밋 상태로 확인된다.

- `workflow/scripts/Common.ps1`, `workflow/scripts/init-workspace.ps1` 수정됨
- `build_guide.js` — 이 프로젝트(계산기 워크플로 검증)와 무관해 보이는
  파일이다. 다른 작업에서 남은 것인지 확인하고, 필요 없으면 검증 시작 전에
  정리한다. **삭제는 사용자가 직접 판단한다.**
- `docs/manual/` — 기존 사용 설명서

이 문서 자체도 `docs/manual/`에 추가되므로, 검증을 시작하기 전에 한 번
커밋해 기준선을 깨끗하게 만드는 것을 권장한다.

```powershell
git add -A
git commit -m "chore: 계산기 검증 시작 전 기준선 정리"
```

## 3. 계산기 앱 사양 (검증용 최소 예제)

의도적으로 작게 잡는다. 목적은 완성도 높은 계산기가 아니라 파이프라인
전 구간을 실제로 통과시키는 것이다.

| 구분 | 내용 |
|---|---|
| 포함 | 덧셈·뺄셈·곱셈·나눗셈, 소수점 입력, 전체 초기화(C), 한 자리 지우기, `=` 연속 사용, 키보드 입력 |
| 제외 | 공학용 함수, 계산 이력 저장, 다중 창, 단위 변환, 프로그래머 모드 |
| 핵심 예외 케이스 | **0으로 나누기** — 크래시 없이 "오류" 표시 후 입력 계속 가능해야 한다 |

0으로 나누기 케이스를 반드시 포함시킨 이유가 있다. 이 조건 하나가
단위 테스트, 모듈 테스트, 그리고 부록 B의 의도적 버그 주입 시나리오까지
관통하는 가장 값싼 인수 조건이기 때문이다.

## 4. 단계별 실행 절차

### 4.0 표기 규칙

- `<모듈>`은 Codex가 STEP 2에서 제안하고 STEP 3에서 확정한 모듈 ID로
  치환한다. 계산기처럼 범위가 작으면 Codex가 단일 모듈로 묶어 제안할
  가능성이 높다. **어떤 이름으로 분해하든 개입하지 않는다** — 모듈 분해는
  Codex의 결정 영역이다(`workflow/rules/claude.md` 3절).
- 현재 `workflow/config.json`의 `mode`는 `"vibe"`다. 즉 이번 검증은
  기본적으로 vibe 모드로 진행되며, 경로 허용 목록 가드는 꺼져 있고 디자인
  버전 폴더는 `v001`이 아니라 `draft` 단일 폴더로 생성된다.

### STEP 1 — 시스템 요구사항 생성 (Codex 호출)

```
/requirements system "간단한 사칙연산 계산기 데스크톱 앱을 만든다. 덧셈, 뺄셈, 곱셈, 나눗셈을 지원하고 0으로 나누면 오류를 표시한다. README.md 를 참고한다."
```

**확인할 것 (V1, V2, V3, V5, V6)**

| 확인 대상 | 기대 결과 |
|---|---|
| `docs/requirements/system/system.md` | 생성됨, 400자 이상, `## 인수 조건` 절 포함 |

### STEP 7 — 구현 (Claude)

여기서부터는 Claude가 직접 `src/`와 `tests/unit/`을 작성한다.

- `src/core/calculator.ts` (또는 Codex가 정한 모듈 구조에 맞는 위치) —
  순수 계산 로직. `electron`을 import하지 않는다.
- `src/main` — 창 생성만. `webPreferences`는 `contextIsolation: true`,
  `nodeIntegration: false`, `sandbox: true`, `webSecurity: true` 유지.
- `src/preload` — `contextBridge.exposeInMainWorld`로 좁은 API만 노출.
- `src/renderer` — React UI.
- `src/shared/ipc.ts` — IPC 채널·타입 정의 (필요한 경우).
- `tests/unit/` — 사칙연산과 0으로 나누기 예외를 포함한 단위 테스트.

```powershell
npx vitest run tests/unit
```

전부 통과해야 다음 단계로 넘어간다.

```powershell
git add -A
git commit -m "feat: <모듈> 계산기 로직 구현"
```

## 5. 부록 B — 의도적 실패 주입 (PRODUCT_CODE_BUG 경로 검증, V10)

자연스러운 1회 통과만으로는 `workflow/rules/claude.md` 6절의 실패 처리
절차가 실제로 동작하는지 확인할 수 없다. 아래를 STEP 8 완료(PASS) 직후에
별도로 수행한다.

1. `src/core`의 나눗셈 또는 뺄셈 로직에 눈에 띄지 않는 버그를 일부러
   심는다. 예: 나눗셈 결과를 반올림 없이 그대로 반환하도록 바꾸거나,
   0으로 나눌 때 오류 대신 `Infinity`를 그대로 반환하게 한다.
2. `npx vitest run tests/unit`이 실패하는지 확인한다(단위 테스트가 이미
   이 케이스를 잡고 있어야 정상).
3. 단위 테스트를 일부러 건드리지 않은 채 `/codex-test module <모듈>`을
   재실행한다.
4. 보고서의 실패 분류를 확인한다.
   - `PRODUCT_CODE_BUG`가 나와야 정상이다. Codex가 원인을 제품 코드로
     정확히 짚었다는 뜻이다.
   - `TEST_OR_REQUIREMENT_SUSPECT`가 나오면 `/codex-recheck module <모듈>`을
     실행해 `PRODUCT_CODE_BUG_CONFIRMED` / `TEST_DEFECT` /
     `REQUIREMENT_SUSPECT` 중 무엇으로 확정되는지 함께 기록한다(V11 관련
     경로이기도 하다).
5. `src/`만 수정해 버그를 되돌린다. `tests/module/`, 요구사항, 인수 조건은
   손대지 않는다.
6. `npx vitest run tests/unit` 통과 확인 후 `/codex-test module <모듈>`을
   다시 실행해 `PASS`로 돌아오는지 확인한다.

```powershell
git add -A
git commit -m "test: PRODUCT_CODE_BUG 경로 의도적 검증 및 복구"
```

## 부록 A — `README.md` 초안 (붙여넣기용)

```markdown
## 1. 개요

사용자가 마우스나 키보드만으로 사칙연산을 빠르고 정확하게 계산할 수 있게
한다.

## 2. 대상 사용자

일반 PC 사용자. 특별한 기술 수준을 요구하지 않는다. 데스크톱 환경에서
사용한다.

## 3. 범위

### 3.1 포함

덧셈, 뺄셈, 곱셈, 나눗셈, 소수점 입력, 전체 초기화(C), 한 자리 지우기,
`=` 연속 사용(직전 결과에 이어 계산), 키보드 입력.

### 3.2 제외

공학용 함수(삼각함수, 로그 등), 계산 이력 저장, 다중 창/탭, 단위 변환,
프로그래머 계산기 모드, 클라우드 동기화.

## 4. 스택과 아키텍처

- Electron + TypeScript + React
- 로컬 전용 데스크톱 앱. 별도 서버 없음
- 빌드: electron-vite
- 테스트: Vitest(unit, module) + Playwright(system)

### 4.1 데이터 저장

없음. 계산 상태를 디스크에 저장하지 않는다. 앱 종료 시 초기화된다.

### 4.2 외부 의존

없음.

## 5. 실행과 테스트

\`\`\`
단위 테스트   npx vitest run tests/unit
모듈 테스트   npx vitest run tests/module/<모듈>
시스템 테스트 npx playwright test tests/system
\`\`\`

## 6. 제약과 결정 사항

| 항목 | 결정 | 근거 |
|---|---|---|
| 지원 OS | Windows 10/11 | 사내 표준 PC 환경 |
| 오프라인 동작 | 항상 오프라인 | 외부 의존이 없는 로컬 전용 앱 |
| UI 언어 | 한국어 | 사용자 전원이 한국어 사용 |
| 성능 목표 | 버튼 입력 후 100ms 이내 반응 | 단순 사칙연산이므로 체감 지연이 없어야 함 |
```
